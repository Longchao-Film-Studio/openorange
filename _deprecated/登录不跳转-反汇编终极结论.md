# 登录不跳转 —— 反汇编终极结论

> 全部结论来自 `GameAssembly.dll` 的**实际反汇编**, 每条都带 RVA。
> 取代此前全部 7 份登录分析(已归档 `_deprecated/`)。

---

## 零、先纠正我上一版的错误

我上一版说「`FPXSDKLoad` 抢占了回调槽」。**这个说法不准确。**

反汇编证明: **`FPXSDKLoad` 根本没有注册回调。**

---

## 一、回调机制的真实结构

### 1.1 回调存在哪

`dump.cs` 第 646003-646010 行:

```csharp
internal class FPXInternal : MonoBehaviour
{
    private static FPXInternal instance;                        // 0x0
    private static readonly object syslock;                    // 0x8
    private static IFPXPlatform platform;                      // 0x10
    internal FPXCallback Callback;                             // 0x18  ★
    internal Queue<ValueTuple<string,string,string>> _cmdQueue; // 0x20
}
```

**回调就是一个字段 `Callback`, 不是列表。**

### 1.2 注册 = 无条件赋值

`FPX.InitCallBack` —— RVA `0x12CFE30`, 全长 **仅 96 字节**:

```asm
0x012CFE6C  call FPXInternal.GetInstance()          ; 取单例
0x012CFE71  test rax, rax
0x012CFE74  je   0x12CFE8B                          ; null -> 报错
0x012CFE76  lea  rcx, [rax + 0x18]                  ; 字段偏移 0x18
0x012CFE7A  mov  qword ptr [rax + 0x18], rbx        ; ★ 直接写, 无判断
0x012CFE86  jmp  0x29FE30                           ; GC 写屏障
```

偏移 `0x18` 正是 `Callback` 字段。

**没有判空、没有「已设置」检查、没有队列、没有 add。纯粹的覆盖写。**

### 1.3 消费 = 每次读当前值

`FPXInternal.Update` —— RVA `0x12CC160`:

```asm
0x012CC191  cmp  qword ptr [rbx + 0x20], 0      ; _cmdQueue == null?
0x012CC196  je   0x12CC1F6                       ; 空则返回
0x012CC1A2  cmp  dword ptr [rax + 0x20], 0       ; Count > 0?
0x012CC1BD  call Queue.Dequeue
0x012CC1C2  mov  r10, qword ptr [rbx + 0x18]     ; ★ 读 Callback (每次循环)
0x012CC1C9  je   0x12CC1EB                       ; null 则跳过
0x012CC1E7  call qword ptr [r10 + 0x18]          ; ★ 调用
0x012CC1F4  jmp  0x12CC1A2                       ; 继续循环
```

**`Update()` 每处理一条消息, 都重新读一次 `Callback` 字段。**

## 二、谁注册了回调 —— 穷举结果

扫描全部相关方法体的 `call` 指令:

| 方法 | RVA | 调用 `InitCallBack`? |
|---|---|---|
| **`FPXSDKBridge.Init`** | 0xF5BCF0 | **✅ 是 (于 0xF5BD8E)** |
| `FPXSDKLoad.InitSDK` | 0x12CD9B0 | **❌ 否** |
| `FPXSDKLoad.Start` | 0x12CE8B0 | **❌ 否** |
| `FPXSDKLoad.OnFpxSdkInitialized` | 0x12CE7D0 | ❌ 否 |
| `FPXSDKLoad.Clear` | 0x5ECA20 | ❌ 否 |
| `FPXSDKLoad.OnAppStartUp` | 0x12CDB90 | ❌ 否 |
| `FPXSDKLoad.InitCrash` | 0x12CD720 | ❌ 否 |

**全部 7 个方法里, 只有一个注册回调: `FPXSDKBridge.Init`。**

`FPXSDKLoad.InitSDK` 实际做的事:

```
GetInstance()  x1
GetPlatform()  x1
Dictionary.Add x5
Dictionary..ctor x2
Debug.Log      x1
RandomRange    x1
```
**它压根不碰回调。**

## 三、那日志为什么显示 FPXSDKLoad?

`FPXSDKLoad.OnFPXCallback` 是**被 `Update()` 调用的**, 因为它就是被注册的那个委托。

`FPXSDKBridge.Init()` 在 `LoadGame.Start()`(日志行 2960) 才执行,
那时 `FPX init` 回调(日志行 56) **早就过去了**。

**但注意: 注册的是"当前 Callback", 之后的消息会用新委托。**
所以理论上 `FPXSDKBridge` 应该能收到**后续**的 login 回调。

## 四、真正的问题在哪

`FPXSDKBridge.OnFPXCallback` 第一句就是 `Debug.Log`(dump 源码第 335093 行),
22 个日志里出现 **0 次**。

既然注册机制是覆盖式的、且 `Update()` 每次都读新值,
那么 0 次的唯一解释是:

> **注册之后, 根本没有新的回调消息进 `_cmdQueue`。**

也就是说 —— **登录动作压根没发生, 或者原生侧没有产生 login 回调。**

这和另一个统计完全吻合:

| 字符串 | 次数 |
|---|---|
| `OnVerifyCodeLoginRet` | **0** |
| `FPX Login success` | **0** |
| `EnterGame` | **0** |

**原生 SDK 从来没有完成过一次登录。**

## 五、结论

> 问题**不是**回调分发被抢占。
>
> 问题是 **原生 FPX.dll 侧根本没有产生登录回调**。

而原生侧要产生 login 回调, 前提是 `/api/login` 返回**它认可**的结果。
